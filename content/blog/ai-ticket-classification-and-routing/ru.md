## Как это работает

ИИ-классификация обращений — это шаг между входящим сообщением и очередью поддержки. Модель читает текст письма, чата или заявки и проставляет **метки**: тема, срочность, язык. Затем **правила маршрутизации** по этим меткам отправляют обращение нужной команде.

Важно разделять две части:

- **Классификация** — задача модели: понять, о чём обращение.
- **Маршрутизация** — обычная бизнес-логика: куда отправить обращение с такими метками.

Так вы меняете структуру команд без переобучения модели, а модель — без переписывания правил.

## Шаг 1. Опишите метки

Начните с короткого и чёткого списка.

- **Тема**: оплата, доставка, технический сбой, возврат, доступ к аккаунту, другое.
- **Срочность**: критично (не работает оплата, утечка данных), высокая, обычная.
- **Язык**: русский, узбекский, английский — чтобы отправить оператору, который на нём говорит.

Правила хорошей схемы:

- Каждая категория имеет **определение и 2–3 примера**.
- Категории не пересекаются. Если оператор сам сомневается, модель тоже будет ошибаться.
- Обязательна категория **«другое»** — модель не должна насильно впихивать обращение в неподходящую тему.

## Шаг 2. Выберите подход

| Подход | Когда подходит |
|---|---|
| LLM с инструкцией и примерами | Быстрый старт, мало размеченных данных, категории часто меняются |
| Обученный классификатор | Много размеченной истории, нужна низкая цена и высокая скорость |
| Ключевые слова и правила | Очевидные случаи: номер заказа, слово «возврат» |

На практике часто комбинируют: правила для очевидного, LLM для остального.

## Шаг 3. Получайте строгий ответ

Просите модель вернуть **JSON** с фиксированными полями и допустимыми значениями. Многие API поддерживают structured output — используйте его.

```json
{
  "topic": "payment",
  "urgency": "high",
  "language": "uz",
  "confidence": "low"
}
```

Проверяйте ответ в коде: если значение не из списка, ставьте «другое» и отправляйте в общую очередь.

## Шаг 4. Настройте маршрутизацию

- Тема → команда: оплата → финансы, сбой → техподдержка второй линии.
- Срочность → приоритет и SLA в helpdesk-системе.
- Язык → оператор с нужным языком.
- **Низкая уверенность** → общая очередь для ручной разметки.

Начните с режима **«подсказки»**: модель предлагает метки, оператор подтверждает. Когда точность устраивает, включайте автоматическую маршрутизацию для части категорий.

## Шаг 5. Измеряйте ошибки

Без измерений вы не узнаете, помогает ли система.

- Соберите **тестовый набор** реальных обращений с ручной разметкой и прогоняйте его при каждом изменении промпта или модели.
- Логируйте каждый случай, когда оператор **переназначил** обращение или **сменил метку**. Это и есть ошибки классификации в продакшне.
- Смотрите метрики **по каждой категории** отдельно: общая точность может скрыть, что критичные обращения теряются.
- Стройте **матрицу ошибок**: какие темы модель путает между собой. Часто это сигнал переписать определения категорий.
- Особо следите за **пропущенными критичными** обращениями — эта ошибка дороже всего.

## Частые ошибки

- Слишком много категорий с размытыми границами.
- Нет категории «другое» и нет ручной очереди.
- Сразу полная автоматизация без этапа подсказок.
- Персональные данные клиентов отправляются во внешний сервис без проверки условий обработки.
- Оценка качества «на глаз» по нескольким примерам.

## FAQ

### Сколько данных нужно для старта?

С LLM можно начать с описаний категорий и нескольких примеров. Для честной оценки качества всё равно соберите набор реальных обращений с ручной разметкой.

### Справится ли ИИ с сообщениями на смеси языков?

Современные LLM обычно понимают смешанные тексты, включая узбекский на латинице и кириллице. Проверьте это на своём тестовом наборе, прежде чем полагаться на метку языка.

### Что делать, если модель ошиблась с критичным обращением?

Добавьте страховку: ключевые слова для критичных ситуаций, которые всегда повышают приоритет, и регулярный разбор пропущенных случаев.
