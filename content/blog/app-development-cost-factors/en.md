## The short answer

There is no universal price. An app costs **team effort × rate**. Effort grows with every feature, screen, platform and integration. The rate depends on who is on the team and which market they work in.

So "how much does an app cost" is better rephrased as: **what scope does the first useful version need**, and who will build it?

## Features: the main price driver

Every feature means screens, server logic, validation and tests. Compare the complexity:

| Feature | Why it is harder than it looks |
| --- | --- |
| **Sign-up and login** | Password recovery, social login, SMS codes, security |
| **Catalog and search** | Filters, sorting, pagination, speed on large data |
| **Payments** | Payment provider, statuses, refunds, receipts |
| **Chat and notifications** | Real time, push, offline mode |
| **Geolocation and maps** | Permissions, accuracy, battery use |
| **Admin panel** | A separate interface, roles, reports |

The admin panel is often forgotten, yet without it the business cannot manage content and orders.

## Platforms: iOS, Android or both

- **Native development** — separate code for iOS and Android. Maximum capability, but effectively two projects.
- **Cross-platform** (Flutter, React Native) — one codebase for both. Usually saves time, though some native features need extra work.
- **PWA** — a web app installable on the phone. The cheapest option, but with limited access to device features.

Platform choice is one of the strongest budget levers. If your audience is mostly on one OS, you can start there.

## Design

- **Standard system components** (Material, Human Interface) — fast and familiar to users.
- **Custom design** with illustrations and animations — more expensive, but a stronger brand.

Each screen is designed in several states: loading, empty, error. More screens mean more work for both the designer and the developers.

## Integrations

Connecting external systems is a common source of unexpected cost:

- payment systems (Payme, Click, Stripe);
- CRM, 1C, inventory systems;
- maps, SMS gateways, analytics;
- the client's own APIs.

A well-documented service connects predictably. A legacy system without documentation can take longer than all the other functionality combined.

## The team and where it is located

An app usually involves a project manager, a designer, mobile and backend developers and a QA engineer. Rates vary widely by country and format:

- **freelancers** — cheaper, but higher risk and more coordination falls on you;
- **a studio** — full cycle and responsibility for the result;
- **an in-house team** — pays off for long-term product development, but requires hiring and management.

## Support after launch

Release is not the finish line. Budget for:

- bug fixes and updates for new iOS and Android versions;
- servers and third-party services;
- new features based on user feedback.

These are recurring costs, not a one-off amount.

## How to cut the budget without losing quality

1. **Start with an MVP** — only the features without which the product does not solve the user's problem.
2. **Pick one platform or go cross-platform** at the start.
3. **Use ready-made services** for authentication, payments and analytics.
4. **Prepare a technical specification** — it reduces rework.
5. **Do not skimp on testing** — bugs after release cost more.

## Common mistakes

- Comparing quotes without comparing scope.
- Ignoring the admin panel and the backend.
- Budgeting only for development and forgetting support.
- Adding features mid-project without revisiting the timeline.

## FAQ

### Why do quotes from different contractors differ so much?

Contractors understand the scope differently: one includes the admin panel, tests and support, another does not. Ask for a breakdown by feature and hours so the quotes can be compared fairly.

### Can I get an exact price before work starts?

An exact price is only possible with a detailed specification. Without it you get a range. Often the first stage is paid discovery and a prototype, after which the estimate becomes precise.

### Which is cheaper: cross-platform or two native apps?

Cross-platform usually takes less effort because the code is shared. But if the app relies heavily on the camera, Bluetooth or complex graphics, native development may be more reliable.
