## Короткий ответ

Для обычного веб-проекта, API или мобильного бэкенда подойдет любой из трех провайдеров: у всех есть виртуальные машины, управляемые базы данных, Kubernetes, объектное хранилище и serverless. Разница проявляется в деталях:

- **AWS** — самый широкий каталог сервисов и самое большое сообщество, проще найти специалиста и готовые решения.
- **Google Cloud** — сильная аналитика данных (BigQuery), удобный управляемый Kubernetes (GKE), развитые AI-сервисы.
- **Azure** — естественный выбор, если компания живет в экосистеме Microsoft: Microsoft 365, Entra ID, .NET, Windows Server.

Решающим часто становится не «какое облако лучше», а то, с чем уже умеет работать ваша команда.

## Сервисы: что как называется

| Задача | AWS | Google Cloud | Azure |
|---|---|---|---|
| Виртуальные машины | EC2 | Compute Engine | Virtual Machines |
| Managed Kubernetes | EKS | GKE | AKS |
| Объектное хранилище | S3 | Cloud Storage | Blob Storage |
| Serverless-функции | Lambda | Cloud Run functions | Azure Functions |
| Контейнеры без серверов | Fargate, App Runner | Cloud Run | Container Apps |
| Управляемые SQL-базы | RDS, Aurora | Cloud SQL, AlloyDB | Azure SQL, Database for PostgreSQL |

Базовые сервисы у всех зрелые. Различия заметны в нишевых вещах: потоковая обработка данных, специфичные базы, инструменты для ML, IoT.

## Как устроены цены

Модель у всех похожа: **оплата по факту потребления** — за часы или секунды работы машин, гигабайты хранения, запросы и исходящий трафик. Скидки дают за обязательства:

- **AWS** — Savings Plans и Reserved Instances за обязательство на 1 или 3 года, Spot-инстансы для прерываемых задач.
- **Google Cloud** — Committed Use Discounts и автоматические скидки за длительное использование некоторых типов машин, Spot VM.
- **Azure** — Reservations, Savings Plan, Spot VM и Azure Hybrid Benefit, если у вас уже есть лицензии Windows Server или SQL Server.

Что обычно недооценивают:

- **Исходящий трафик** (egress) — платный у всех трех и при большой отдаче контента может стать заметной статьей.
- **Управляемые сервисы** дороже «голых» машин, но экономят время на администрирование.
- **Цены отличаются по регионам** — одна и та же машина в разных регионах стоит по-разному.

Точную оценку дают официальные калькуляторы каждого провайдера. Сравнивайте конкретную конфигурацию, а не прайс за «одну машину».

## Регионы рядом с Центральной Азией

На момент написания ни у одного из трех провайдеров нет региона в Узбекистане или соседних странах. Ближайшие варианты обычно находятся в трех направлениях:

- **Европа** — Франкфурт, Варшава, Стокгольм и другие.
- **Ближний Восток** — ОАЭ, Бахрейн, Катар, Саудовская Аравия (набор зависит от провайдера).
- **Индия** — Мумбаи, Дели, Хайдарабад, Пуна (тоже зависит от провайдера).

Проверьте задержку из Ташкента до конкретных регионов собственными замерами — география и маршруты трафика не всегда совпадают. И учтите требования к локализации персональных данных: если закон обязывает хранить их в стране, зарубежный регион для этой части данных не подойдет.

## Бесплатные уровни

У всех трех есть стартовые предложения для новых аккаунтов: кредиты на пробный период и **постоянно бесплатные лимиты** на часть сервисов. Условия регулярно меняются, поэтому:

- читайте актуальную страницу free tier перед стартом;
- сразу настройте **бюджет и оповещения о расходах** — случайно оставленный ресурс быстро съедает кредиты;
- не стройте продакшен в расчете на бесплатный уровень.

## Как выбрать: короткий чек-лист

1. Что знает команда? Опыт с одним облаком экономит месяцы.
2. Какие управляемые сервисы нужны именно вам — проверьте, есть ли они в нужном регионе.
3. Где пользователи и есть ли требования к хранению данных?
4. Какая экосистема уже используется: Microsoft 365, Google Workspace, свои серверы?
5. Как вы будете платить: доступны ли подходящие способы оплаты и выставление счетов для вашей компании.

Частая ошибка — выбирать по разнице в цене одной виртуальной машины. На реальном счете важнее трафик, управляемые базы и время инженеров.

## FAQ

### Можно ли использовать несколько облаков сразу?

Можно, но это усложняет сеть, безопасность и учет расходов. Для небольшой команды обычно разумнее одно основное облако, а мультиоблако имеет смысл при конкретной причине: требовании заказчика, уникальном сервисе или юридических ограничениях.

### Сложно ли потом переехать к другому провайдеру?

Зависит от того, насколько глубоко вы используете уникальные сервисы. Приложения в контейнерах с PostgreSQL переносятся сравнительно легко, а проекты на специфичных базах и serverless-интеграциях одного провайдера — заметно сложнее.

### Подойдет ли большое облако маленькому сайту?

Технически да, но часто это избыточно. Для простого сайта удобнее VPS, обычный хостинг или платформы вроде Vercel. Крупное облако оправдано, когда нужны управляемые сервисы, масштабирование и гибкая инфраструктура.
