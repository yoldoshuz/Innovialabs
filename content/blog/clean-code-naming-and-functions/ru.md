## Главное правило

Код читают намного чаще, чем пишут. Поэтому цель — чтобы другой разработчик (или вы через полгода) понял фрагмент **без лишних усилий**. Ниже — правила, каждое с примером «до» и «после».

## Имена раскрывают смысл

Имя должно отвечать на вопрос «что это и зачем», без расшифровки.

```typescript
// До
const d = 30;
const arr = users.filter(u => u.a);

// После
const trialPeriodDays = 30;
const activeUsers = users.filter(user => user.isActive);
```

Практические правила:

- **Переменные — существительные**: `invoice`, `totalAmount`.
- **Функции — глаголы**: `calculateTotal`, `sendInvoice`.
- **Булевы значения — вопрос**: `isPaid`, `hasAccess`, `canEdit`.
- **Без магических чисел**: выносите их в именованные константы.
- **Единый словарь**: если в проекте `fetch`, не смешивайте с `get`, `load` и `retrieve` для одного и того же.
- Длина имени соразмерна области видимости: `i` в цикле на три строки допустимо, в модуле — нет.

## Функция делает одно дело

Если для описания функции нужно слово «и», скорее всего, её стоит разделить.

```typescript
// До
function processOrder(order: Order) {
  if (!order.items.length) throw new Error("Empty order");
  let total = 0;
  for (const item of order.items) total += item.price * item.qty;
  db.save({ ...order, total });
  mailer.send(order.email, `Сумма: ${total}`);
}

// После
function processOrder(order: Order) {
  validateOrder(order);
  const total = calculateTotal(order.items);
  saveOrder(order, total);
  notifyCustomer(order.email, total);
}
```

Теперь верхняя функция читается как оглавление, а каждую часть можно тестировать отдельно. Жёсткого лимита строк нет, но если функцию приходится прокручивать — это повод задуматься.

## Мало аргументов

Чем больше параметров, тем легче перепутать порядок. Булевы флаги особенно коварны: по вызову не понять, что значит `true`.

```typescript
// До
createUser("Ali", "ali@example.com", true, false, "ru");

// После
createUser({
  name: "Ali",
  email: "ali@example.com",
  isAdmin: true,
  sendWelcomeEmail: false,
  locale: "ru",
});
```

Ориентир: до двух-трёх аргументов. Больше — передайте объект с именованными полями. Флаг, меняющий поведение функции, часто означает, что это две разные функции.

## Ранний возврат вместо вложенности

Глубокие `if` заставляют держать в голове все условия сразу. Обрабатывайте особые случаи сразу и выходите.

```typescript
// До
function getDiscount(user: User | null) {
  if (user) {
    if (user.isActive) {
      if (user.orders > 10) {
        return 0.1;
      }
    }
  }
  return 0;
}

// После
function getDiscount(user: User | null) {
  if (!user || !user.isActive) return 0;
  if (user.orders <= 10) return 0;
  return 0.1;
}
```

Основной сценарий остаётся на верхнем уровне отступа, а «охранные» проверки стоят в начале.

## Комментарии объясняют «почему»

Комментарий, пересказывающий код, устаревает и мешает. Полезный комментарий объясняет неочевидную причину.

```typescript
// До
// увеличиваем счётчик на 1
retries++;

// После
// API провайдера иногда отвечает 503 при пиковой нагрузке,
// поэтому повторяем запрос, а не показываем ошибку сразу
retries++;
```

Если хочется написать комментарий «что делает этот блок», сначала попробуйте вынести блок в функцию с понятным именем.

## Чек-лист перед коммитом

- Понятно ли по имени, что хранит переменная и что делает функция?
- Делает ли каждая функция одно дело?
- Есть ли функции с тремя и более аргументами или булевыми флагами?
- Можно ли убрать вложенность ранним возвратом?
- Не пересказывают ли комментарии код?
- Не осталось ли закомментированного кода? Для истории есть Git.

## FAQ

### Насколько короткой должна быть функция?

Универсального числа нет. Ориентир — функция делает одно дело на одном уровне абстракции и помещается на экран без прокрутки.

### Длинные имена — это плохо?

Нет, если они точные. `calculateMonthlyRevenue` лучше, чем `calc`. Плохо, когда имя длинное из-за повторов или лишних слов вроде `Data`, `Info`, `Manager`.

### Можно ли применять эти правила к старому проекту?

Да, постепенно: улучшайте код, который всё равно меняете в рамках задачи. Массовый рефакторинг без тестов рискован.
