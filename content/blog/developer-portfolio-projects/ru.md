## Что работодатель ищет в портфолио

Портфолио отвечает на вопрос, который резюме оставляет открытым: **умеете ли вы довести задачу до результата**. Работодатель смотрит не на количество проектов, а на:

- **законченность** — проект работает, его можно открыть;
- **самостоятельность** — видно ваши решения, а не повтор урока;
- **качество кода** — структура, понятные имена, отсутствие мусора;
- **умение объяснить** — почему сделано именно так.

Обычно достаточно **2–4 сильных проектов**. Лучше три доведённых до конца, чем десять брошенных на половине.

## Какие проекты впечатляют

Хороший проект решает понятную задачу и содержит хотя бы одну нетривиальную часть.

| Тип проекта | Почему работает |
|---|---|
| Инструмент для реальной проблемы | Есть пользователь и осмысленные требования |
| Проект с внешним API и обработкой ошибок | Показывает работу с реальными данными |
| Приложение с авторизацией и базой данных | Полный цикл: от интерфейса до хранения |
| Вклад в open source | Умение читать чужой код и работать по правилам проекта |
| Проект для знакомого бизнеса или организации | Реальные пользователи и обратная связь |

Подбирайте проекты под желаемую роль. Frontend-разработчику важны интерфейс, адаптивность и доступность. Backend — архитектура API, работа с базой, тесты. Data-аналитику — исследование с выводами и визуализацией.

## Чего избегать

- **Клоны из туториалов один в один**: очередной список задач или клон известного сервиса, повторённый по видео, не показывает ваших навыков. Если делаете клон, добавьте значимые собственные функции и опишите их.
- **Незаконченные проекты** без описания и с неработающим демо.
- **Ключи и пароли в репозитории**: это сразу заметный красный флаг.
- **Один гигантский коммит** «initial commit» со всем кодом.
- **Десятки мелких учебных репозиториев** на первом плане, за которыми теряются сильные работы.

## Как оформить проект

### README

README — это витрина проекта. Рекрутер может не открыть код, но README прочитает. Минимальная структура:

```markdown
## Название проекта

Одна фраза: что делает и для кого.

Демо: ссылка · Скриншот или GIF

## Возможности
- Ключевая функция 1
- Ключевая функция 2

## Стек
React, TypeScript, Node.js, PostgreSQL

## Как запустить
npm install
npm run dev

## Решения и сложности
Почему выбран такой подход, что было трудно и как решено.
```

### Демо

Работающая ссылка снимает главный барьер: человек видит результат за несколько секунд. Для фронтенда подойдёт бесплатный хостинг статических сайтов, для мобильных приложений — видео или GIF с основными сценариями. Если демо требует входа, дайте тестовый аккаунт в README.

### Разбор проекта

Короткий текст на 1–2 экрана — в README, блоге или на сайте-портфолио:

- какую задачу решали;
- какие варианты рассматривали и почему выбрали этот;
- что пошло не так и как исправили;
- что улучшили бы сейчас.

Такой разбор часто становится темой разговора на собеседовании и показывает инженерное мышление лучше, чем сам код.

## Где разместить портфолио

- **GitHub** с закреплёнными лучшими репозиториями — обязательно для разработчика.
- **Простой сайт-портфолио** с карточками проектов: название, описание, стек, ссылки на демо и код.
- **Ссылки в резюме и LinkedIn** на конкретные проекты, а не только на профиль.

Сайт-портфолио не обязан быть сложным. Важнее, чтобы он быстро открывался, нормально выглядел на телефоне и вёл к проектам за один клик.

## FAQ

### Сколько проектов нужно в портфолио?

Обычно хватает 2–4 законченных проектов, подобранных под желаемую роль. Качество и оформление важнее количества.

### Можно ли включать учебные проекты с курсов?

Можно, если вы существенно их доработали и в README честно указано, что было основой, а что добавлено вами. Проект, повторённый по уроку без изменений, лучше не выносить на первый план.

### Нужен ли дизайн, если я backend-разработчик?

Сложный интерфейс не нужен. Достаточно понятного README, документации API и, по возможности, простого способа проверить работу — например, коллекции запросов или минимального клиента.
