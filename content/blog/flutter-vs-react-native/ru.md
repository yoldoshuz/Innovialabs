## Короткий ответ

Универсального победителя нет. **Flutter** удобен, когда нужен единый фирменный дизайн и предсказуемый вид на всех устройствах. **React Native** выгоден, когда в компании уже есть веб-разработчики на React и хочется переиспользовать их опыт и часть кода. Для большинства бизнес-приложений оба варианта рабочие, и решающим часто становится состав команды.

## Модель отрисовки

Это главное техническое различие.

- **Flutter** не использует системные кнопки и списки. Он рисует каждый пиксель интерфейса своим движком на собственном холсте. Поэтому приложение выглядит одинаково на iOS и Android и не зависит от особенностей системных компонентов.
- **React Native** описывает интерфейс в JavaScript, а на экране появляются **настоящие нативные компоненты** iOS и Android. Приложение ближе к «родному» поведению платформы, но мелкие визуальные различия между iOS и Android приходится учитывать.

## Язык

| | Flutter | React Native |
|---|---|---|
| Язык | Dart | JavaScript / TypeScript |
| Порог входа | Нужно выучить новый язык, но он простой и строго типизированный | Знаком любому веб-разработчику |
| Типизация | Встроенная, строгая | Через TypeScript, который стал стандартом де-факто |

**Dart** похож на Java, Kotlin и TypeScript одновременно, поэтому опытный разработчик осваивает его быстро. Но вне Flutter он используется редко. **TypeScript** — один из самых распространенных языков, и навыки легко переносятся между вебом, сервером и мобильной разработкой.

## Единообразие интерфейса

- Во Flutter интерфейс совпадает до пикселя на всех платформах. Хорошо для сильного бренда и кастомного дизайна.
- В React Native вид ближе к системному. Хорошо, когда важно, чтобы приложение ощущалось привычным для пользователя каждой платформы.

Оба подхода позволяют сделать и кастомный, и «системный» интерфейс — вопрос в том, что потребует меньше усилий.

## Экосистема

- **Flutter:** пакеты публикуются на pub.dev. Многие базовые вещи (виджеты, анимации, навигация) есть «из коробки» от команды Flutter, поэтому меньше зависимости от сторонних библиотек.
- **React Native:** доступен огромный мир npm и экосистема React. Платформа **Expo** заметно упрощает старт, сборку и обновления. Но качество сторонних библиотек сильно различается, их нужно выбирать внимательно.

В обоих случаях для редких нативных функций может понадобиться собственный модуль на Swift или Kotlin.

## Рынок найма

- React-разработчиков на рынке больше, а веб-разработчик может перейти в React Native относительно быстро. Но опыт веба не равен опыту мобильной разработки: публикация, производительность и нативные модули требуют отдельных знаний.
- Flutter-разработчиков меньше в абсолютных числах, зато специалисты обычно сфокусированы именно на мобильной разработке.

Перед выбором стоит посмотреть, кого реально можно нанять в вашем городе или на удаленке.

## Типичное соответствие проектам

- **Flutter:** приложения с насыщенным кастомным дизайном, анимациями, единым брендом; проекты, где мобильная команда отдельная; приложения, которые потом могут выйти и на десктоп.
- **React Native:** продукты, где уже есть веб на React; команды, которые хотят делиться логикой между вебом и мобайлом; приложения, близкие к стандартным паттернам iOS и Android.

## Таблица для выбора

| Ваша ситуация | Склоняйтесь к |

| Есть команда на React / TypeScript | React Native |
| Нужен пиксель в пиксель одинаковый дизайн | Flutter |
| Много сложных кастомных анимаций | Flutter |
| Хочется делиться кодом с веб-проектом | React Native |

## Частые ошибки

- **Выбирать по бенчмаркам из интернета.** Для обычного бизнес-приложения оба фреймворка достаточно быстры; узкое место чаще в коде и API.
- **Игнорировать команду.** Лучший фреймворк — тот, на котором ваша команда уверенно пишет и который вы сможете поддерживать.
- **Не проверять ключевые библиотеки.** Если приложение зависит от конкретного SDK (платежи, карты, оборудование), убедитесь, что для него есть поддерживаемый пакет.

## FAQ

### Что быстрее работает — Flutter или React Native?

В типичных сценариях пользователь разницы не заметит. Оба фреймворка позволяют сделать плавное приложение; производительность больше зависит от качества кода, чем от выбора между ними.

### Можно ли сменить фреймворк потом?

Можно, но это переписывание клиентской части. Backend и API при этом обычно остаются, поэтому их стоит проектировать независимо от выбора мобильного стека.

### Какой фреймворк проще поддерживать годами?

Оба поддерживаются крупными компаниями (Google и Meta) и активно развиваются. Долгосрочная поддержка больше зависит от дисциплины команды: регулярные обновления, минимум заброшенных зависимостей, тесты.
