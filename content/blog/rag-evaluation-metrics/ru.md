## Коротко: почему метрики нужно разделять

RAG состоит из двух частей: **поиска** (retrieval) и **генерации** (LLM). Плохой ответ может появиться по двум разным причинам: нужный документ не нашёлся или модель его нашла, но исказила. Одна общая оценка «ответ хороший/плохой» не говорит, что чинить.

Поэтому метрики считают **по слоям**: сначала качество найденного контекста, затем качество ответа относительно этого контекста.

## Метрики поиска

Для них нужен тестовый набор: вопрос и список документов (или чанков), которые действительно содержат ответ.

| Метрика | Что показывает |
|---|---|
| **Recall@k** | Есть ли хотя бы один нужный документ в топ-k |
| **Precision@k** | Какая доля из топ-k действительно релевантна |
| **MRR** | Насколько высоко стоит первый правильный документ |
| **nDCG@k** | Качество ранжирования с учётом степени релевантности |
| **Context precision** | Много ли «шума» попало в контекст для LLM |

Пример подсчёта recall@k и MRR:

```python
def recall_at_k(retrieved, relevant, k):
    return int(any(doc in relevant for doc in retrieved[:k]))

def reciprocal_rank(retrieved, relevant):
    for i, doc in enumerate(retrieved, start=1):
        if doc in relevant:
            return 1 / i
    return 0.0
```

Средние значения по всему тестовому набору — это ваши recall@k и MRR.

## Метрики генерации

Здесь оценивается ответ модели:

- **Faithfulness (верность контексту)** — все ли утверждения ответа подтверждаются найденными фрагментами. Низкое значение означает галлюцинации.
- **Answer relevance** — отвечает ли ответ на заданный вопрос, а не на соседний.
- **Correctness** — совпадает ли ответ с эталонным, если эталон есть.
- **Citation accuracy** — ссылается ли модель на те фрагменты, откуда взяла факт.

## Как считать метрики генерации

Ручная разметка надёжна, но дорога. На практике используют **LLM-as-a-judge**:

1. Разбейте ответ на отдельные утверждения.
2. Для каждого спросите модель-судью: подтверждается ли оно контекстом? Ответ — да или нет.
3. Faithfulness = доля подтверждённых утверждений.

Чтобы судье можно было доверять:

- Дайте ему **чёткие критерии** и бинарные решения вместо шкалы от 1 до 10.
- Проверьте его на **небольшой выборке, размеченной людьми**, и посмотрите, насколько оценки совпадают.
- Используйте **фиксированный промпт и модель**, иначе результаты разных прогонов несравнимы.

Существуют готовые библиотеки для оценки RAG, но логику метрик стоит понимать самостоятельно, чтобы правильно читать результаты.

## Диагностика: где именно сбой

| Recall поиска | Faithfulness | Вероятная причина | Что делать |
|---|---|---|---|
| Низкий | Любой | Нужный контекст не находится | Чанкинг, эмбеддинги, гибридный поиск |
| Высокий | Низкий | Модель выдумывает поверх контекста | Промпт, инструкции цитировать, другая модель |
| Высокий | Высокий, но ответ не по теме | Плохая answer relevance | Переписывание запроса, промпт |
| Высокий, но низкий context precision | Падает | Слишком много шума в контексте | Реранкер, меньше k |

## Как построить процесс оценки

- Соберите **тестовый набор из реальных вопросов** пользователей, включая сложные и «без ответа».
- Добавьте вопросы, на которые система должна честно сказать **«не знаю»**.
- Запускайте оценку **при каждом изменении**: модели, промпта, чанкинга, поиска.
- Меняйте **одну вещь за раз**, иначе не поймёте, что повлияло.
- Читайте плохие примеры глазами — цифры показывают где, а примеры — почему.

## FAQ

### Сколько вопросов нужно в тестовом наборе?

Начните с того, что можно разметить быстро и качественно, — даже небольшой набор лучше, чем ничего. Постепенно добавляйте реальные вопросы, особенно те, на которых система ошиблась.

### Можно ли оценивать RAG без эталонных ответов?

Частично да. Faithfulness и answer relevance считаются без эталона — по вопросу, контексту и ответу. А вот correctness и метрики поиска требуют разметки.

### Насколько можно доверять LLM-судье?

Настолько, насколько он совпадает с людьми на вашей выборке. Регулярно сверяйте его оценки с ручной разметкой и не используйте одну и ту же модель как генератор и единственного судью без проверки.
