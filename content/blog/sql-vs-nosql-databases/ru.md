## Главное различие

**SQL-базы** (реляционные) хранят данные в таблицах со строгой схемой: заранее известно, какие есть столбцы и какого они типа. Таблицы связаны ключами, а запросы пишутся на языке SQL. Примеры: PostgreSQL, MySQL, SQL Server.

**NoSQL** — это не одна технология, а общее название для баз, которые устроены иначе. Они отказываются от части возможностей реляционной модели ради гибкости структуры, особого способа хранения или простоты горизонтального масштабирования.

Вопрос «что лучше» неверен. Правильный вопрос — **какая модель данных лучше подходит вашей задаче**.

## Четыре основных типа NoSQL

- **Документные** (MongoDB, CouchDB). Данные хранятся как JSON-подобные документы. Один документ может содержать вложенные объекты и массивы — например, товар со всеми характеристиками.
- **Ключ-значение** (Redis, Memcached). Самая простая модель: по ключу получаете значение. Очень быстро, идеально для кэша и сессий.
- **Колоночные** (Cassandra, HBase). Рассчитаны на огромные объёмы записей и распределение по многим серверам. Их не стоит путать с колоночными аналитическими СУБД вроде ClickHouse — те как раз работают с SQL.
- **Графовые** (Neo4j). Хранят узлы и связи между ними, удобны для запросов вида «друзья друзей» или рекомендаций.

## Сравнение по ключевым параметрам

| Параметр | SQL | NoSQL |
|----------|-----|-------|
| Схема | Строгая, меняется через миграции | Часто гибкая, задаётся приложением |
| Связи | JOIN между таблицами | Обычно через вложенность или дублирование |
| Согласованность | Транзакции ACID — стандарт | Зависит от системы: от строгой до «итоговой» (eventual) |
| Масштабирование | Чаще вертикальное, плюс реплики для чтения | Многие системы изначально рассчитаны на горизонтальное |
| Язык запросов | Единый стандарт SQL | У каждой системы свой API |
| Сложные отчёты | Сильная сторона | Обычно сложнее |

Пара уточнений, чтобы не попасть в мифы:

- Современные SQL-базы умеют хранить JSON (в PostgreSQL для этого есть тип `jsonb`), так что гибкие поля — не повод сразу уходить в NoSQL.
- Многие NoSQL-системы поддерживают транзакции и настраиваемую согласованность. Нужно смотреть возможности конкретной базы, а не категорию в целом.
- «Гибкая схема» не означает «без схемы». Структура всё равно существует — просто контролировать её приходится в коде.

## Таблица выбора

| Задача | Что обычно подходит |
|--------|---------------------|
| Интернет-магазин, заказы, платежи | SQL |
| CRM, ERP, учётные системы | SQL |
| Каталог с очень разными атрибутами товаров | SQL с JSON-полями или документная база |
| Контент, CMS, профили с вложенными данными | Документная база или SQL |
| Кэш, сессии, счётчики, лимиты запросов | Ключ-значение (Redis) |
| Логи и события в огромных объёмах | Колоночная NoSQL или аналитическая СУБД |
| Рекомендации, социальные связи | Графовая база |
| Полнотекстовый поиск | Поисковый движок (Elasticsearch) рядом с основной базой |

## Как принять решение

1. **Опишите данные.** Если сущности тесно связаны (клиент — заказ — товар — оплата), это реляционная модель.
2. **Оцените требования к точности.** Деньги, остатки, бронирования требуют надёжных транзакций — SQL здесь проверенный выбор.
3. **Посмотрите на запросы.** Нужны отчёты с группировками и объединениями — SQL. Нужно «достать объект целиком по id» — документ или ключ-значение.
4. **Не переоценивайте масштаб.** Хорошо настроенная реляционная база с индексами и репликами выдерживает нагрузку большинства проектов.
5. **Учитывайте команду.** Технология, которую команда знает, обычно надёжнее модной.

Нормальная практика — **сочетать базы**: PostgreSQL как основное хранилище, Redis для кэша, Elasticsearch для поиска.

## Частые ошибки

- Выбирать NoSQL «потому что не нужно продумывать схему» — потом это оборачивается беспорядком в данных.
- Хранить связанные финансовые данные в базе без надёжных транзакций.
- Пытаться построить сложную отчётность на системе ключ-значение.
- Добавлять третью и четвёртую базу без реальной необходимости — каждая требует поддержки, бэкапов и мониторинга.

## FAQ

### NoSQL быстрее, чем SQL?

Не в целом. Отдельные NoSQL-системы очень быстры в своём сценарии, например Redis при чтении по ключу. Но на запросах со связями и агрегациями хорошо настроенная SQL-база часто оказывается удобнее и быстрее.

### Можно ли потом перейти с одной модели на другую?

Можно, но это заметная работа: нужно переделать структуру данных, запросы и перенести данные. Поэтому модель стоит выбирать по характеру данных с самого начала.

### Что выбрать для стартапа?

Если нет особых требований, разумно начать с PostgreSQL или MySQL. Реляционная база закрывает большинство задач, а NoSQL можно добавить позже под конкретную нагрузку.
