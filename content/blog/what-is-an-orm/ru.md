## Что такое ORM

**ORM (Object-Relational Mapping)** — это слой между кодом приложения и реляционной базой данных. Вы описываете модели — `User`, `Order`, `Product` — а ORM сопоставляет их с таблицами, превращает вызовы методов в SQL и возвращает результат в виде объектов.

Вместо строки `SELECT * FROM users WHERE is_active = true` вы пишете что-то вроде `User.objects.filter(is_active=True)`, а ORM сама соберёт запрос, подставит параметры и создаст объекты.

## Популярные ORM

| ORM | Язык | Особенности |
|---|---|---|
| **Prisma** | TypeScript, JavaScript | Схема в отдельном файле, сгенерированный типизированный клиент, встроенные миграции |
| **Django ORM** | Python | Часть фреймворка Django, миграции и админка из коробки |
| **SQLAlchemy** | Python | Гибкая библиотека: и высокоуровневая ORM, и конструктор SQL-выражений |
| **Hibernate** | Java | Реализация стандарта JPA, модели описываются аннотациями `@Entity` |

Так выглядит один и тот же запрос «активные пользователи с заказами» в Prisma:

```ts
const users = await prisma.user.findMany({
  where: { isActive: true },
  include: { orders: true },
});
```

## Плюсы

- **Скорость разработки.** Типовые операции создания, чтения и обновления пишутся в одну строку.
- **Безопасность.** Параметры подставляются автоматически, что защищает от SQL-инъекций при обычном использовании.
- **Миграции.** Изменения схемы фиксируются в коде и применяются одинаково на всех окружениях.
- **Типизация и автодополнение.** Особенно у Prisma и современных версий SQLAlchemy: ошибки в названиях полей видны до запуска.
- **Переносимость.** Сменить PostgreSQL на MySQL проще, хотя на практике это редко бывает бесплатно.

## Минусы

- **Скрытые запросы.** Одна строка кода может породить десятки SQL-запросов.
- **Неоптимальный SQL** для сложных отчётов, оконных функций и специфичных возможностей базы.
- **Ещё одна абстракция.** Чтобы отлаживать производительность, всё равно нужно понимать SQL и индексы.

## Проблема N+1

Самая известная ловушка ORM. Вы получаете список из N записей одним запросом, а затем в цикле обращаетесь к связанному объекту — и ORM для каждой записи делает ещё один запрос. Итого N+1 запрос вместо одного-двух.

```python
# Django: 1 запрос за заказами + по запросу на каждого клиента
for order in Order.objects.all():
    print(order.customer.name)

# Исправлено: заказы и клиенты загружаются одним запросом с JOIN
for order in Order.objects.select_related("customer"):
    print(order.customer.name)
```

На локальной базе с десятью заказами разницы не видно. В продакшене с тысячами строк и сетевой задержкой страница начинает грузиться секундами.

Как это решают в разных ORM:

- **Django** — `select_related` для связей «один к одному» и «многие к одному», `prefetch_related` для «один ко многим».
- **SQLAlchemy** — опции загрузки `selectinload` и `joinedload`.
- **Prisma** — `include` или `select` со связанными моделями.
- **Hibernate** — `JOIN FETCH` в JPQL-запросе или entity graphs.

Главное — **включить логирование SQL** в разработке и смотреть, сколько запросов делает каждая страница.

## Когда лучше обычный SQL

- **Отчёты и аналитика**: сложные агрегации, оконные функции, CTE.
- **Массовые операции**: обновить или вставить сотни тысяч строк за раз.
- **Специфичные возможности базы**: полнотекстовый поиск, JSONB-операторы, upsert с особыми условиями.
- **Критичные по скорости запросы**, где нужен полный контроль над планом выполнения.

Почти все ORM позволяют выполнить сырой SQL там, где это нужно. Нормальная практика — ORM для большей части типовой работы и SQL для узких мест.

## FAQ

### Нужно ли знать SQL, если используешь ORM?

Да. ORM упрощает написание запросов, но не отменяет их. Без SQL сложно понять, почему страница тормозит, и правильно добавить индексы.

### Какую ORM выбрать для нового проекта?

Обычно ту, что принята в вашем стеке: Prisma или аналоги для TypeScript, Django ORM для Django-проектов, SQLAlchemy для остальных Python-сервисов, Hibernate для Java. Смотрите на качество миграций и удобство отладки запросов.

### Как найти N+1 в существующем проекте?

Включите логирование SQL или профилировщик вроде Django Debug Toolbar и откройте медленную страницу. Повторяющиеся однотипные запросы с разными ID — верный признак N+1.
