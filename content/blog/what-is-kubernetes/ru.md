## Kubernetes в двух словах

**Kubernetes** (K8s) — это платформа **оркестрации контейнеров**. Вы описываете желаемое состояние: «запусти три копии API, открой их по такому адресу, выдели столько памяти». Kubernetes постоянно сравнивает реальность с описанием и исправляет расхождения: перезапускает упавшие контейнеры, переносит их с отказавшего сервера, раскатывает новые версии.

Docker отвечает на вопрос «как упаковать и запустить один контейнер». Kubernetes — «как управлять сотнями контейнеров на десятках серверов, чтобы всё работало без ручного вмешательства».

## Из чего состоит кластер

Кластер Kubernetes делится на две части.

**Control plane** — «мозг» кластера:

- **API server** — единая точка входа. Все команды (`kubectl`, CI/CD, панели) идут через него.
- **etcd** — хранилище состояния кластера: что должно быть запущено и где.
- **Scheduler** — решает, на какой ноде запустить новый контейнер, исходя из свободных ресурсов.
- **Controller manager** — набор контроллеров, которые приводят реальное состояние к желаемому.

**Ноды (worker nodes)** — серверы, где работают приложения:

- **kubelet** — агент на ноде, который запускает контейнеры по указаниям control plane.
- **container runtime** — среда, которая непосредственно запускает контейнеры (например, containerd).
- **kube-proxy** — отвечает за сетевую маршрутизацию к сервисам.

В управляемых сервисах облачных провайдеров control plane обслуживает провайдер, а вы работаете только с нодами и своими приложениями.

## Что Kubernetes автоматизирует

- **Самовосстановление.** Контейнер упал — перезапуск. Нода отказала — поды переезжают на другие.
- **Масштабирование.** Число копий можно менять одной командой или автоматически по нагрузке.
- **Обновления без простоя.** Rolling update постепенно заменяет старые копии новыми и умеет откатываться.
- **Service discovery и балансировка.** Сервисы находят друг друга по имени, трафик распределяется между копиями.
- **Конфигурация и секреты.** Настройки и пароли хранятся отдельно от образа.
- **Декларативность.** Вся инфраструктура описана в YAML-файлах, которые хранятся в Git и проверяются на ревью.

## Когда Kubernetes не нужен

Kubernetes решает реальные проблемы, но сам по себе сложен. Ему нужны знания, время на поддержку, мониторинг и обновления кластера. Честные признаки того, что проекту он пока не нужен:

- приложение работает на **одном-двух серверах** и это устраивает;
- сервисов **немного**, и они редко меняются;
- в команде **нет человека**, готового разбираться с кластером;
- короткий простой при деплое **допустим**;
- проект на стадии **MVP**, и главная задача — быстро проверить гипотезу.

В таких случаях хватает **Docker Compose** на сервере, **PaaS-платформы** или управляемых контейнерных сервисов облака. Перейти на Kubernetes позже проще, если приложение уже упаковано в контейнеры и настроено через переменные окружения.

## Когда Kubernetes оправдан

- много сервисов, которые разные команды выпускают независимо;
- нагрузка заметно меняется, и нужно автоматическое масштабирование;
- требования к **отказоустойчивости**: падение одного сервера не должно останавливать продукт;
- частые релизы и нужна единая стандартная схема деплоя;
- несколько окружений (dev, staging, prod), которые должны быть одинаковыми.

## Как принять решение

| Вопрос | Скорее Compose / PaaS | Скорее Kubernetes |
|---|---|---|
| Сколько серверов? | один-два | несколько и больше |
| Сколько сервисов? | единицы | десятки |
| Есть DevOps-экспертиза? | нет | да |
| Допустим простой? | да, короткий | нет |
| Нагрузка | стабильная | пиковая, растущая |

Если большинство ответов в левой колонке — начинайте проще. Документация проекта: [kubernetes.io](https://kubernetes.io/docs/concepts/overview/).

## FAQ

### Kubernetes заменяет Docker?

Нет. Docker (или другой инструмент) собирает образы, а Kubernetes управляет их запуском на кластере. Образы, собранные Docker, работают в Kubernetes без изменений.

### Можно ли запустить Kubernetes на одном сервере?

Да, есть лёгкие дистрибутивы для одного узла. Но главное преимущество — устойчивость к отказу сервера — при этом теряется, а сложность остаётся.

### Что выбрать: свой кластер или управляемый?

Для большинства команд управляемый кластер проще: обновления и доступность control plane берёт на себя провайдер. Свой кластер имеет смысл при особых требованиях к размещению данных или инфраструктуре.
